# Arms map

Hub for `vault/arms/`: one usage note per arm, a tool that brings a model into Pluto or takes one out. The C# lives
in `scripts/arms/` and loads with the lib through `scripts/lib/Config.ps1` (one Add-Type batch, PowerShell 5.1, C# 5).
- **The viewer arms** write `<outBase>.bin` (v4) and `<outBase>.features.json` (the sidecar). Drop both on the viewer
  together.
- **The model builders** (`Build-Pipe.ps1`, `Build-Frame.ps1`) write a solver's own files (`.cii`, `.s2k`, `.std`) and
  workbooks, with the same viewer pair as a preview.

## Plant (production side, SQL exports)

- [[vault/arms/plant-combined-to-viewer|plant-combined-to-viewer]] — **start here for the combined workflow**: pipes + steel + bbox fallback → one `CombinedToPluto` file, end to end.
- [[vault/arms/pipe-csv-to-viewer|pipe-csv-to-viewer]] — SP3D piping: v4 CSV → `PipeCsvReader` (room filter, sizing, progress bar) → `PipeToPluto` → viewer. Pipe-size groups; `PartOid` labels.
- [[vault/arms/steel-csv-to-viewer|steel-csv-to-viewer]] — W-shape members: row-per-member CSV with dims, local-Y vector and SP3D cardinal point → `SteelToPluto` I-sections. Section-name groups.
- [[vault/arms/calc-room-map|calc-room-map]] — calc PDFs → run names (Windows PDF IFilter, no packages) → rooms via the v4.2 pipe CSV → room-to-calc CSV. Code in `scripts/voyager/`, the transfer crate for Voyager code (Voyager itself never leaves the D: machine).

## Pipe stress and frame models (branch `pipestress`)

- [[vault/arms/pipe-and-frame-workflow|pipe-and-frame-workflow]] — **start here for pipe stress and frame models**: how the pipe model, the frame model, their workbooks, CAESAR II, SAP2000, STAAD.Pro and the viewer connect (diagrams), and the commands for each job: edit a CAESAR job, start a line, view CAESAR's results, seed SAP's check model, edit a SAP frame model, run the probes.
- [[vault/arms/pipe-workbook|pipe-workbook]] — the pipe model as an Excel workbook (Settings, Elements, Sections, Processes, Restraints, SIFs, Forces, Displacements, Uniform, Wind, Joints, Hangers, Nozzles, Coords, Materials; a hidden exact base) written from a `.cii`, a TOML or a template and read back by `Build-Pipe.ps1 -In x.xlsx`: edits by Id, unchanged values exact (an unedited workbook gives the source `.cii` byte for byte), errors by cell address; `-Watch` rebuilds the preview on every save and the viewer's Auto-reload follows; `-Cii` guards a `.cii` changed outside. A form: notes, dropdowns, red / amber cells for what the build would refuse, a Start page with live checks, a live 3D View, live node numbering. Its Materials sheet feeds the SAP check model.
- [[vault/arms/pipe-builder|pipe-builder]] — a pipe-stress model from a parametric TOML config (runs, bends, branches with tees, sections, valves / flanges / reducers / expansion joints / couplings, supports by type or single DOF with gaps, stiffness, friction, CNODEs, node-to-node ties, SIFs, ΔT and pressures, forces / imposed displacements / uniform loads / wind) → `PipeBuilder` → `CaesarNeutralWriter` → a `.cii` for CAESAR II, via `scripts/caesar/Build-Pipe.ps1`. The same runner imports a `.cii` losslessly (byte-identical when unedited), saves the exact model (`-Json`) and compares two models by meaning (`-Compare`). What CAESAR files confirm, and what comes from CAESAR's documentation (listed as notices).
- [[vault/arms/caesar-checks|caesar-checks]] — CAESAR II's error checker caught before CAESAR: its errors, warnings and notes (bend angles and bend nodes, corrosion, overspecified displacements, loop closure, node range, SIFs, intersections, thin wall, reducers, expansion joints, mixed uniform loads, temperatures read as expansions) as Pluto's review codes, in the viewer's Checks tab, `-Cii`'s `[checks ]` lines and the workbook's red / amber cells and Start counts; what is not checked and why.
- [[vault/arms/caesar-to-viewer|caesar-to-viewer]] — CAESAR II pipe stress: neutral file (`.cii`) + the Excel output → `CaesarNeutralReader` (read by structure; checked on 15.01 and 11.00) → `CaesarGeometry` (bends as arcs, checked against CAESAR's coordinate report) → `CaesarResults` (one report per tab; `.xls` / `.xlsb` through Excel) → `CaesarToPluto` via `scripts/caesar/Run-Caesar.ps1`. Tapered reducers, valve bow-ties; per load case displacements (deformed shape), element forces, code stresses and restraint loads; one sidecar `supports` item per support node, drawn as 3D symbols by the viewer (branch `pipestress`).
- [[vault/arms/staad-design-workbook|staad-design-workbook]] — a model's STAAD design and output requests in `<model>.design.xlsx`, beside the frame workbook: parameter sets (code, method, units), parameters by group or member list in a spreadsheet, and the run (checks, selection, prints, commands) in order. `-Std` writes it after the analysis, names resolved against the model and refused when missing; `-In x.std -Xlsx` writes it from the `.std`.
- [[vault/arms/frame-workbook|frame-workbook]] — SAP2000 frame models (piping, ducting, steel; links, springs, releases, loads, cases) in an Excel workbook like the CAESAR one: `Build-Frame.ps1 -In x.s2k -Xlsx`, edit in Excel, `-Preview -Watch` for the live viewer, a live 3D View, `-S2k` / `-Open` for SAP, `-Std` for STAAD.Pro and `-In x.std` back from it; a lossless round trip from a SAP export; a CAESAR job's seeded check model is edited here too. The SAP probe settles which tables SAP reads.
- [[vault/arms/workbook-kit|workbook-kit]] — the workbook machinery the CAESAR and SAP frame workbooks share (`scripts/arms/workbook/Wb*`): form and kinds, Start sheet, launchers, the hidden base, reading back, refresh, the formula evaluator, the live 3D view's projection and frame (`WbPlot`); extracted 2026-11-05 with every CAESAR workbook byte-identical.

## Solvers

- [[vault/arms/sap-controller|sap-controller]] — **read first for anything that drives SAP2000**: the one C# controller (`scripts/sap/SapSession.cs` + `Run-Sap.ps1`), its capability table, the facts it relies on. Python calls the runner; it never touches the OAPI.
- [[vault/arms/sap-export-model|sap-export-model]] — **any model SAP2000 holds → viewer in one command** (`Run-Sap.ps1 -Export`, or the wrapper `pythonTools/sap/export_model.py`): attach or second instance, run on a working copy if results are missing, the analysis mesh (not the objects) renumbered 1..N over the OAPI, results streamed to `.s2k`, `SapToPluto`. Written for the <project> tank.
- [[vault/arms/sap-s2k-to-viewer|sap-s2k-to-viewer]] — SAP2000: `.s2k` model + results → `SapToPluto` (the model read losslessly through `S2kDoc` and the frame model, SAP axes kept) → v4 shells with per-corner forces and global displacements, and frames with sections, local axes, offsets, releases and text labels; sidecar groups, supports, links, loads by pattern / case / combination, frame properties and the build's checks. `Build-Frame -Preview` draws through it too.
- [[vault/arms/sap-results-coverage|sap-results-coverage]] — results side of the SAP arm: every shell / frame / joint / link quantity SAP2000 holds against what the controller pulls and what `SapToPluto` shows (shell forces, moments and stresses per corner, displacements, frame end forces, fibre stresses, station envelopes); still missing: link forces and gap openings in the viewer, reactions, true multi-station beam fields.
- [[vault/arms/sap-tank-builder|sap-tank-builder]] — the Python tank generator (`pythonTools/sap/tankbuilder`): what each feature is in the model (courses, baseplate, roof + gutter ring, gap support layer, ring wall, dents, meridional edge refinement with `pythonTools/sap/edge_profile.py` to read the edge rows), the plans for ports and surveys, how to check the ring-wall section, and which SAP tables are still unverified.
- [[vault/arms/sap-tank-model-diagrams|sap-tank-model-diagrams]] — the model in three generated pictures: loads and case chain, shell local axes on wall / baseplate / roof, beam node connectivity at the eave and the rim.
- [[vault/arms/settlement-profiles|settlement-profiles]] — ground displacement on the ground joints (`[settlement]`, trench first): config, the audit CSV + generated SVG (plan heatmap + elevation) beside the model, and the on-demand vault copies (`--vault-svg`, `run_sap.py --figures`). Runs on the real tank are project records in the Notes vault, not here.
- [[vault/arms/beam-offset-study|beam-offset-study]] — the tank's three-joint gap chain built four ways (coincident at centroid / top with Transform=No / top with Transform=Yes / true elevations) as a beam and as a ring on SAP 26: equivalent under vertical load and settlement (A = B = C, X within 0.4 %), so C — no coincident joints — is the layout to move the tank to; the `Transform` column finding. `pythonTools/sap/offset_study.py [--ring] --run`.
- [[vault/arms/ring-wall-load-path|ring-wall-load-path]] — the ring wall in pictures (SVG assets): tangential-only restraints in plan, and the rim → contact gap → wall → soil gap → ground section with the SAP 26 check numbers.
- [[vault/arms/staad-frame-to-viewer|staad-frame-to-viewer]] — STAAD.Pro frame results: a frame model's `.anl` → `AnlFrameReader` → `StaadToPluto` via `scripts/staad/Run-StaadFrame.ps1`. Members with STAAD's axes, sections (SAP's library by name, else fitted to STAAD's member properties), releases, offsets and supports; per load case the member end forces, joint displacements, reactions and code check ratios (a `CHECK CODE` under a one-case `LOAD LIST` goes into that case; any other is an entry of its own).
- STAAD, the other way. Writing a frame model as a STAAD.Pro `.std` is `Build-Frame.ps1 -Std`, and `-In <x>.std` reads one back into a frame model, STAAD's edits too ([[vault/format/frame-to-staad|frame-to-staad]]); the reading is the `.anl` reader's (`StaadInput` in `scripts/lib/readers/ANLReader.cs`), extended to a `.std`'s input commands. The post-processing lib itself (`scripts/lib/`: `.anl` readers, DSRs, section cuts, STAAD input generation) has no arm note yet; the sanitized-lib audit (Notes vault) holds its re-hydration state.
