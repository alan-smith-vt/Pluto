# Pluto 2026-11-24b: STAAD results in the viewer; SAP <-> frame workbook <-> STAAD, a merge, probe round 4, a STAAD design workbook

Cloud session on `pipestress`, the one of [[vault/handoffs/handoff-2026-11-23|handoff-2026-11-23]], continued. The
user asked whether the frame `.anl` reader the other session brought in ([[vault/handoffs/handoff-2026-11-24|handoff-2026-11-24]])
works with Pluto's binary and the viewer. It did not: it wrote CSV files only. Then they asked about code checks.

Of the ways offered, the user chose a viewer arm, with code ratios per load case: "the user can provide a load list
for code checks and staad will output results per load combo".

> [!info]- What was built
> - **`scripts/arms/StaadToPluto.cs`** and the runner **`scripts/staad/Run-StaadFrame.ps1`**: a frame `.anl` → `<base>.bin`
>   (v4, beams only, Y up, inches) + `<base>.features.json`. It reads the file through `AnlFrameReader`, refuses what
>   the reader marks as an error and passes its warnings on.
> - **Drawn:**
>   - members with STAAD's local axes, releases and offsets;
>   - sections from SAP's library by name (STAAD's older AMERICAN names tried as AISC's; single angles turned to
>     STAAD's principal axes), else fitted to `PRINT MEMBER PROPERTIES`, PRIS as given;
>   - supports as sidecar items.
> - **Per load case:**
>   - member end forces, as the force inside the member at each end (end A's printed force negated, so tension is
>     positive and both ends read alike);
>   - joint displacements (the deformed shape);
>   - reactions (kind `restraint`, colouring the support symbols);
>   - `Code ratio` and `Code case` (kind `code`).
> - **Code checks.**
>   - A `CHECK CODE` under a one-case `LOAD LIST` goes into that case, beside its forces.
>   - Any other check is an entry of its own: each member's governing ratio and case.
>   - Where one code was checked case by case, one more entry holds each member's largest ratio over those cases.
>   - Sidecar groups of the members that FAIL and of those NOT DESIGNED, per code.
> - **Changed in shared code:**
>   - `AnlFrameMember.PropertyInches` (the unit where a member's property stands, for PRIS numbers);
>   - `SapToPluto.FrameSection` is `internal`, so the arm draws a library shape as the SAP arm does.
> - **`viewer/tests/readback_staad.js`** checks an export through the viewer's own reader. `--probe` checks the
>   probe's printed numbers.
> - **Vault:**
>   - [[vault/arms/staad-frame-to-viewer|staad-frame-to-viewer]] (new);
>   - the Arms map;
>   - [[vault/arms/pipe-and-frame-workflow|pipe-and-frame-workflow]] (diagram and runner table);
>   - [[vault/format/v4-schema|v4-schema]] (kind `code`);
>   - the probes' README.

> [!info]- Verified here

> - **The probe's `.anl`:**

## Later: the design moves into the frame workbook (2026-11-25)

The user was not convinced by the separate design workbook: they want each member's parameters on a list of members
that follows the geometry, and asked about live formulas or Power Query. Both keep the list live but leave typed
values behind when a row is inserted, deleted or sorted. So the values go on the member's own Frames row, and the
separate file is dropped ([[vault/arms/staad-design|staad-design]]).

**Built:**
- **`StaadDesign` rides in the model** (`FrameDesign.cs`), in tables of Pluto's own:
  - a frame's values are a record of the frame (`PLUTO STAAD MEMBERS`), so they follow a rename, a split, a deletion
    and a merge;
  - the sets, the rows by list (a set's ALL values, links, later sets) and the run are three more tables.
- **The frame workbook:** a STAAD block of columns on the Frames rows (a column group), a read-only Groups column to
  filter by, and the sheets STAAD sets, STAAD parameters and STAAD run.
- **`StdToFrame`** reads a `.std`'s commands after the analysis into the design, STAAD's numbers and groups translated
  to the model's labels. The first set's parameter lines go to the frames they name, as STAAD reads them (a later line
  wins).
- **`FrameStd`** writes the design from the model: one line per parameter and value, with the members that share it.
- **The read-back check** compares designs as STAAD reads them, not as text.
- **`FrameMerge`** carries the design from the master, the frames' values by label.
- **`Build-Frame`:** `-Design` and the `.design.xlsx` are gone (a leftover one gets a warning). `-NewDesign` now goes
  with `-Xlsx` or `-Std` and stores a starter in the model.
- **Removed:** `FrameDesignWorkbook.cs`.

**The split question.** The user asked whether the split at `-Xlsx` is still needed. It is: it is what makes the
workbook hold the split frames, and the design rows need each row to be one STAAD member. The second call, in `-Std`,
still covers a `.s2k` written straight to `-Std` and a joint added on a span since. Nothing was obsolete but an unused
overload of `FrameMesh.SplitAtJoints`, removed. A piece split at `-Std` takes its frame's design values, with a notice.

**Checked in the session:**
- the round 4 probe: `.std` → model → `-Std`, and through the workbook, identical as STAAD reads it;
- the round 4 SAP-leg and saved files: read and written back identical;
- typed values, a renamed frame, a deleted frame, a second set, DJ1 / DJ2 by joint label, refusals by cell;
- a SAP rack with `-NewDesign`;
- the runner under pwsh 7 for `.std` → workbook → `.std`, `-S2k`, and SAP's export with `-Merge`;
- an unedited workbook reads back to its base as before;
