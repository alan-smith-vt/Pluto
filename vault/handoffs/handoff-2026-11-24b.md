# Pluto 2026-11-24b: a STAAD frame's results in the viewer, code ratios per case

Cloud session on `pipestress`, the one of [[vault/handoffs/handoff-2026-11-23|handoff-2026-11-23]], continued. The
user asked whether the frame `.anl` reader the other session brought in ([[vault/handoffs/handoff-2026-11-24|handoff-2026-11-24]])
works with Pluto's binary and the viewer. It did not: it wrote CSV files only. Then they asked about code checks.

Of the ways offered, the user chose a viewer arm, with code ratios per load case: "the user can provide a load list
for code checks and staad will output results per load combo".

> [!info]- What was built
> - **`scripts/arms/StaadToPluto.cs`** and the runner **`scripts/staad/Run-StaadFrame.ps1`**: a frame `.anl` → `<base>.bin`
>   (v4, beams only, Y up, inches) + `<base>.features.json`. It reads the file through `AnlFrameReader`, refuses what
>   the reader marks as an error and passes its warnings on.
> - **Drawn:**
>   - members with STAAD's local axes, releases and offsets;
>   - sections from SAP's library by name (STAAD's older AMERICAN names tried as AISC's; single angles turned to
>     STAAD's principal axes), else fitted to `PRINT MEMBER PROPERTIES`, PRIS as given;
>   - supports as sidecar items.
> - **Per load case:**
>   - member end forces, as the force inside the member at each end (end A's printed force negated, so tension is
>     positive and both ends read alike);
>   - joint displacements (the deformed shape);
>   - reactions (kind `restraint`, colouring the support symbols);
>   - `Code ratio` and `Code case` (kind `code`).
> - **Code checks.**
>   - A `CHECK CODE` under a one-case `LOAD LIST` goes into that case, beside its forces.
>   - Any other check is an entry of its own: each member's governing ratio and case.
>   - Where one code was checked case by case, one more entry holds each member's largest ratio over those cases.
>   - Sidecar groups of the members that FAIL and of those NOT DESIGNED, per code.
> - **Changed in shared code:**
>   - `AnlFrameMember.PropertyInches` (the unit where a member's property stands, for PRIS numbers);
>   - `SapToPluto.FrameSection` is `internal`, so the arm draws a library shape as the SAP arm does.
> - **`viewer/tests/readback_staad.js`** checks an export through the viewer's own reader. `--probe` checks the
>   probe's printed numbers.
> - **Vault:**
>   - [[vault/arms/staad-frame-to-viewer|staad-frame-to-viewer]] (new);
>   - the Arms map;
>   - [[vault/arms/pipe-and-frame-workflow|pipe-and-frame-workflow]] (diagram and runner table);
>   - [[vault/format/v4-schema|v4-schema]] (kind `code`);
>   - the probes' README.

> [!info]- Verified here
> - **The compile:** the C# 5 compile of the arm, the reader and the SAP arm under mono, with no warnings in them.
> - **The probe's `.anl`:**
>   - with a scratch SAP library holding its shapes: 8 sections from the library, the 2L fitted (the scratch library
>     has no 2L), the PRIS 6 in square;
>   - without a library: all fitted (W10X49 within 0.02 in).
>
>   `readback_staad.js --probe` passes both:
>   - forces end A negated, a fixed-ended beam's end moments the same sign;
>   - reactions and displacements as printed;
>   - check 1's ratios and cases;
>   - the angle turned 45°.
> - **A scratch copy of the probe** with one-case `LOAD LIST`s before four checks put their ratios in cases 101, 102
>   and 301. It made the repeated check of 101 an entry of its own, and gave the largest-over-cases entry.
> - **The runner** parses, and under pwsh 7 it checks its paths and refuses an output inside the repo. Its `Export`
>   call needs .NET Framework (the sidecar's `System.Web.Extensions`), so the end-to-end run is the production
>   machine's.
